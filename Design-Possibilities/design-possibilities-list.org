* Design Possibilities Capture List

There are so many possibilities for Great Design!

This is a semi-ordered list of design-related topics that may or may
not yet be well-addressed.

This document is currently focused on capturing design ideas.

** Entity Categorization, Overlap, Blur!

Many computational entities are hybrids with aspects of
- Computer Languages
- Databases
- Operating Systems

"Platforms" can apply to any of these
- Since they are designed for us to build on

"Tools" can apply to any of these and more!

Where possibilities are listed here under one of these categories,
consider how it might apply to entities in other categories and/or
entities which are hybrids or which otherwise blur these categories!

*** Desirable Features in Programming Languages

**** Simplicity

- No unnecessary built-in features to Language Core
- User-Interface is via
  - smart Browsers
  - Browser/Editors
  - Refactoring Command Tools
  - Database query languages customized for this task
    - e.g. like how Postgres allows such domain-specific customization
- Tools can provide much of the user-view
  - Suppress unwanted details
    - Code Folding
    - Suppress or show inferrable details
      - detailed types, contracts, comments
    - Short or Long aliases - in preferred human language(s)
  - Algebraic vs. Parenthesized Polish (Lisp)

Convenience Features belong to Tool Level
- e.g. Scheme-Like Declarative Macros
  - Tools can show code with or without them
    - Change of viewpoint or refactor in either direction

*** Desirable Features in Lisp-Like Languages

**** Leverage Keywords more

- Macro Keyword Syntax: (define: x as: value)
  - Macro names always keywords, since not evaluable!

- Keyword Syntax: (proc from: x to: y with: z)
  - would automatically create parameters: from, to, with
  - as in Smalltalk

- Keyword Aliases: (proc source:src:s x destination:dst:d y with:&: z)
  - can use source: src: s: et al equivalently as keywords for arguments
  - can use source, src, s et al are equivalent names for the same
    parameter binding
  - tools can
    - warn about inconsistency
    - help ensure consistency, especially in a single scope
    - provide tool-tips
  - Documentation could be tacked on, e.g.:
    source:src:s:"orgmode document path"

*** XML, XHTML, HTML Evolved!

**** Easy Pieces

HTML and XHTML become XML documents with suitable namespaces!
- Namespaces apply to attributes!
- Classes can have attributes
  - Instead of <tag classes="hide,boxed",hidestyle="ellipsis",hideto="sidebar",...>
  - Use: <tag.hide[style=ellipsis,to=sidebar].boxed[...]>
    - quotes optional unless value has special characters
  - Like simple CSS Selector syntax!

**** Simpler Element Syntax
- Span elements could use unicode characters
  - instead of <...> </...>
  - specifiable inside or outside the document
- Non-span elements could use line-oriented syntax
  - e.g. Lines beginning with ! or ? or .
    - How to group affected lines?

**** Radical Ideas
- Full spec of allowed features in namespace URL!
  - Looseness can & must be specified too!
- Close to programming-language typing model
  - Available types specified in namespace URL definition
- Tags could be replaced with Classes!
- Documents could map to linked tuples in RDBMSs.
  - and be a type in PostgreSQL!
  - PostgreSQL could have types for all XML components!
  
**** Names for XML Evolved?
